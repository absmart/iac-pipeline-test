## 4. Bootstrap the remote state

Terraform keeps each environment's state in Azure Storage, which has to exist before anything can use it. bootstrap/ is a small Terraform configuration that creates it, and scripts/bootstrap-state.sh runs it.

Each state account has shared keys and public access off, TLS 1.2, versioning and 30 days of soft delete, locally redundant storage and a lock against deletion. Each environment has its own container, and its pipeline identities only get access to that container.

The first run applies with local state, then moves the bootstrap's own state into e2etfstateprdeus201st (container bootstrap, blob bootstrap.tfstate), where the pipelines can't reach it. Run the script again whenever you add an environment.

You need Terraform 1.10 or later, and the right to create resource groups and storage accounts and to assign roles in the state subscription(s).

```bash
az login
bash scripts/bootstrap-state.sh
```

## 5. Create the identities in Azure

The pipeline signs in to Azure with OIDC (workload identity federation), so no secret is stored anywhere. Each environment gets a user-assigned managed identity to deploy, and a read-only one that plans, so code in a pull request can't change anything.

The deploy identity has Contributor at the deployment scope. You need Owner (or Contributor and User Access Administrator) at those scopes.

It gives each identity access to its environment's state container, and stops if the bootstrap hasn't created the state storage yet.

The script writes the IDs the next step needs to pipeline-values.env.

```bash
az login
bash scripts/setup-azure.sh
```

## 6. Set up the repository

The script stores the identities' client IDs as repository variables. For each environment it creates a deployment environment with its reviewers and an <env>-plan environment for its plans, each allowing only the branch or tag it deploys from.

It adds a ruleset to main requiring a pull request and the plan checks, and blocking force pushes and deletion.

```bash
gh auth login
bash scripts/setup-github.sh
```

## 7. Add the pipeline in a pull request

Copy the generated files into the repository on a new branch and open a pull request into main. The rulesets are in force, so this is the first change that goes through them.

```bash

git add .github/workflows/iac-pr.yml .github/workflows/iac-deploy.yml .github/workflows/iac-drift.yml
git commit -m "Add the infrastructure pipeline"
git push -u origin add-iac-pipeline
gh pr create --fill
```

## 8. Check the pull request

validate checks formatting and syntax and runs Checkov. Each plan job signs in as its environment's plan identity and shows what would change.

Each plan is posted to the pull request as a comment, updated on every push.

If a plan fails to sign in, compare the error's subject with the federated credentials in the identities table.

## 9. Merge and approve

Each push to a deploying branch or tag runs IaC deploy for its environments in turn. Each is planned, then waits for the environment's reviewers: open the run, read the plan in the summary, and choose Review deployments.

The deploy job applies the plan the reviewer saw. If anything changed in between, the apply stops and the next run plans again.

Check:

- [ ] deploy (dev) succeeds after a push to main.
- [ ] deploy (prd) succeeds after a push to main and approval.
